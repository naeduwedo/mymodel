# ADR-019 - 打包只发布二进制与配方，绝不包含用户数据或运行时

**状态：** 已接受（Task 9 的实现决策）

## 背景

安装程序决定的不只是文件落在哪里：它还决定卸载之后什么会保留、降级可能损坏什么，以及崩溃
报告里可能包含什么。这里有三种诱人的捷径是错的：

- 把 llama.cpp 及其 CUDA 库一起塞进安装包，这会在发布包时冻结运行时，并让下载体积增加
  约 200 MB；
- 卸载时删除数据目录，这会把用户等了好几个小时才下载完的模型扔掉；
- 在构建脚本里生成自签名证书，这会产生安装时带吓人警告、且无法被信任的包。

## 决策

1. **包中只包含二进制和元数据。** 模型、运行时和数据库位于每用户的数据目录（规格 §15），
   并在首次运行时创建。
2. **卸载保留用户数据。** Linux 的 `preremove.sh` 打印路径；MSIX 则从一开始就从不写应用
   自身数据目录之外的任何位置。
3. **运行时独立更新。** 它们按用户安装，不属于任何安装程序。
4. **签名是发布步骤，不是构建步骤。** 脚本产出未签名的产物；信任决定属于发布它们的人。
5. **包版本来自 `Cargo.toml`**，在构建时替换进 MSIX manifest，因此版本永远不会与二进制不一致。

## 让卸载/升级可以承受的安全特性

| 风险 | 缓解措施 |
| --- | --- |
| 降级损坏模式 | `MigrationError::TooNew` 拒绝打开由更新版本构建写入的数据库 |
| 升级丢失数据 | `Database::open_with_backup` 在迁移前复制数据库，复制失败则中止 |
| 客户端与核心不一致 | `protocol` 版本出现在 `gguf version --json` 中；不一致会在握手时被拒绝 |
| 崩溃不留证据 | panic hook 写入 `crash-<ms>.log`；`gguf doctor` 按路径列出它们 |

## 已验证 vs. 仅编写

| 平台 | 状态 |
| --- | --- |
| Windows MSIX | **已构建**：69.8 MB 的包；`makeappx unpack` 报告成功，并列出三个核心二进制以及外壳 |
| Linux deb/rpm | 只有配方；当时没有可用的 Linux 机器，CI 必须先构建它，之后才能这样声称 |
| macOS DMG | 只有配方；它将要包含的 SwiftUI 外壳仍在计划中 |

这种划分是刻意的。写三个安装程序并宣布 Task 9 完成，只会产出两个从来没有人构建过的产物。
