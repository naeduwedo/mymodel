# ADR-017 - 按设备的预算与会过期的租约，绝不汇总为一个池

**状态：** 已接受（Task 7 的实现决策）

## 背景

规格 5.4 禁止把多块 GPU 的显存之和作为一个池呈现，并要求每一次分配都携带预算、预留和释放。
这里有两条诱人的捷径是错的：

- 把所有显存加总，并针对总量做规划，这会产出任何运行时都无法执行的方案（一个 20 GiB 的
  张量无法跨越两张卡，除非运行时按层切分）；
- 跟踪分配却没有截止期限，于是崩溃的工作进程永久占着它的预留，GPU 在核心重启之前都不可用。

## 决策

1. **预算按设备划分。** 对每张卡独立计算
   `usable = observed_free - engine_reserve - safety_margin`。
   空闲显存未知时得到零可用字节，而不是乐观的猜测。
2. **规划器是一个纯函数**，输入为（设备、预算、需求、策略、运行时事实）。只有当某个策略能在
   这台机器上、用这个运行时执行时，它才返回该策略。
3. **每一次预留都是带 TTL 的租约。** 过期的租约可以被回收，因此崩溃无法把设备钉死。
4. **多 GPU 策略拦截的是拆分，而不是加载。** 当 `allow_multi_gpu` 为 false，或者两张卡来自
   不同厂商且未显式选择加入时，规划器退回到 CPU 卸载，而不是直接失败：模型仍可能运行在
   一张卡加主机内存上。

## 后果

- 规划器无需 GPU 即可被穷尽测试；17 个测试覆盖了本项目真实的 4090 + 3060 配置上的策略阶梯。
- 用户能看到*为什么*：每个方案和每一次拒绝都附带一句话，指明其依据的数字和策略。
- 只有当运行时声明支持时才提出张量并行，因为它是最可能在加载时失败的策略。

## 验证

真实机器（RTX 4090 + RTX 3060，空闲 22.0 + 11.8 GiB）：

    8 GiB  -> single_gpu      (fits the 4090: 19.5 GiB usable)
    20 GiB -> layer_split     (19.5 + 2.2 GiB across both)
    60 GiB -> cpu_offload     (28.8 GiB VRAM total, rest in RAM, stated as slower)
