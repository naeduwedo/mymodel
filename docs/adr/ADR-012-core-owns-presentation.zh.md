# ADR-012 — 核心负责表现层，外壳只负责渲染

**状态：** 已接受（Task 3 的实现决策）

## 背景

规格 §4 要求三个原生 UI 共享一套信息架构和同样的措辞。对「如何描述一个降级状态的核心」
做三份独立实现必然会产生漂移：一个说 *降级*，另一个说 *部分可用*，第三个只看了 HTTP
状态码，于是显示一个绿点。

另一种设计——每个外壳自己调用 `HealthService` 并格式化拿到的结果——还会在第二个方面失败：
它把策略放进了 UI。判定 `dropped > 0` 应当给出警告，或者判定某项计划中的能力应当置灰而
不是隐藏，这是必须只做一次的产品决策。

## 决策

核心暴露 `UiService/GetSnapshot`（`proto/ui.proto`），其返回值恰好是 Overview 页和
Settings 页所需的内容：

- 带**预格式化**值的卡片，附一个严重级别和一条可选的详情行；
- 能力行，带一个状态词、一个严重级别，以及该能力不可用的原因；
- 设置行，带 `editable`（本构建中为 false）和一条解释原因的注记；
- 配置检查发现的问题，挂在它们所涉及的字段上。

外壳只渲染这份载荷，别的什么都不做。外壳可以选择*表现形式*（winUI 的 `InfoBar`、GTK 行、
SwiftUI 列表），但不能决定*含义*。

## 后果

- 重命名一个标签或修改一个阈值，就是 Rust 里的一行改动，且无需 UI 工具包即可测试。
- 这份载荷可以端到端测试：`gguf overview` 会打印它，Windows 外壳的单元测试则断言映射关系。
  从而避免了三套无法验证的外壳。
- 核心因此携带少量它本不需要的文案。这正是要点：这是带有产品含义的文案。
- 外壳无法展示核心未声明的能力，规格规则 4 因此在三套代码库中都保持成立。
- 本地化 UI 就意味着本地化核心的字符串。目前接受这一点；等到确有必要，可以在
  `UiSnapshotRequest` 中加一个 locale 字段。

## 被否决的备选方案

| 备选方案 | 不予采用的原因 |
| --- | --- |
| 每个外壳读取 `HealthReport` 并自行格式化 | 策略会泄漏到三套代码库中；漂移不可避免 |
| 外壳共享一个 C# / Rust / Swift 库 | 三套工具链，一个 FFI 接口面，而且文案仍无单一事实来源 |
| 一个本地 HTTP+HTML UI | 规格 §1.2 明确禁止把浏览器 UI 作为主界面 |
