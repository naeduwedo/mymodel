# ADR-015 — 下载完整性：就绪前先校验，原子提交

**状态：** 已接受（Task 5 的实现决策）

## 背景

规格 §7.3 要求 ETag / SHA-256 校验、断点续传、原子写入，以及“下载完成 → 校验 → 注册”。
一个看起来已就绪、实则只下了一半的 40 GB 文件，比缺失的文件更糟：故障会在推理时才暴露，
离它产生的原因很远。

## 决策

下载器强制执行严格的顺序：

1. **预检查** —— 在任何字节移动之前，先确认目标路径是被包含的（不含 `..`，不是绝对路径）。
2. **暂存** 到目标文件旁边的 `<name>.part`，若已存在部分文件，则通过 HTTP `Range` 请求续传。
3. **校验** —— 暂存文件必须与 Hub 发布的 SHA-256 匹配。
4. **提交** —— 一次原子重命名把它移到最终位置，因此崩溃不会留下一个看起来很像样的短文件。

有两条完整性规则很容易弄错，它们由测试强制保证：

- **没有已发布哈希**的文件会被拒绝（`Unverifiable`），而不是凭信任就标记为就绪；
- **忽略 `Range`** 的服务器会返回 `200` 而不是 `206`，因此客户端会重新开始暂存文件，
  而不是把整个文件追加到自己的前缀之后。

只有校验通过的文件才会以 `ready` 写入注册表（规格 §7.3）。

## 后果

- `model-hub` 是唯一写入模型文件的地方；注册表是唯一记录它们已就绪的地方，而且只有在拿到
  哈希时才会记录。
- Token 是可选的，绝不写入日志，`HubClient` 的 `Debug` 实现会将它们脱敏（派生的 `Debug`
  会在第一行日志里泄露 token）。
- 网络测试是选择性开启的（`GGUF_HUB_TESTS=1`），否则会明确失败；一个被静默跳过的网络测试
  比一个失败的测试更糟。

## 验证

- 5 个针对真实 Hub 的选择性测试：搜索、目录树列取、一次真正下载并校验提交、一次哈希损坏的
  拒绝（不留任何残留），以及一个仍然通过校验的续传部分文件。
- 端到端：`gguf models pull` 下载 `stories260K.gguf`，校验 SHA-256，注册它，
  `gguf models list` 显示解析出的 commit 和架构。
